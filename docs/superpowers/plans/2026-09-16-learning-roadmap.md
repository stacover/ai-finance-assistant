# 金融研究 Agent 学习与项目实施路线

> 建立日期：2026-09-16。此文档是分阶段学习路线，不授权助手自动代写全部核心功能。进入具体阶段时使用 `superpowers:executing-plans` 逐项推进，并遵守根目录 `AGENTS.md` 的人工学习分工。

**Goal:** 做出能结合行情与上传文档回答研究问题、提供证据和执行轨迹、在失败时明确说明限制的金融研究助手，并能解释其实现与取舍。

**Architecture:** 沿用现有模型网关、知识库、研究 Agent 和配置中心四个模块。学习主线是单 Agent 的可靠执行、工具编排、上下文和评估；知识库作为其中一种数据工具，工程部分由助手补齐。

**Tech Stack:** 以当前 POM 为基线：Java 17、Spring Boot 3.5.14、Spring AI 1.0.0、Maven，以及已有 MySQL/MyBatis-Plus、Nacos 配置。版本来自代码，不代表已验证全部服务兼容性；阶段内不顺便升级依赖。

**需求依据：** 用户希望学习 Agent 实战并积累求职项目；核心代码亲手实现，基础代码由助手完成。协作规则见 [AGENTS.md](../../../AGENTS.md)。

## 目标范围与节奏

用户已确认每周投入 6–8 小时；暂按 Java 后端 / Agent 应用开发方向规划，具体目标岗位尚待确认。预估从当前基础到可演示版本约 8–12 周，是排期参考，不是完成承诺；按验收结果推进，不按日期强行过关。

每周建议安排两次 60–90 分钟核心实现、一次验证与复盘，其余时间用于阅读项目涉及的概念。每次学习以一个能够解释并验证的小目标结束。

2026-09-16 调整：用户明确重点学习 Agent。学习时间大致按 Agent 核心 70%、RAG 应用基础 15%、作品整理与复盘 15% 分配；这是安排目标，不是已投入时间统计。保持原阶段编号便于追踪，实际学习顺序改为 **M0 → M1 → M4 → M5 → M2/M3 → M6**，知识库工程由助手在需要接入时补齐。

### RAG 学习深度边界

- 必须理解：文档切分、Embedding、相似度检索与 TopK 各起什么作用；检索到的内容可能无关或过期；相似度高不代表结论正确。
- 必须会用：通过一个知识库工具获取带来源的片段，决定是否继续查证，回答时引用证据，无证据时说明限制，并识别文档里的指令不是系统指令。
- 助手负责：向量存储选型适配、入库持久化、批量向量化、去重、文件管理、页码修补与辅助测试。用户了解流程和接口，不逐项手写。
- 暂不深入：向量索引原理、Embedding 模型训练/微调、复杂分块优化、混合检索和重排算法。只有后续评估明确暴露检索瓶颈，或目标岗位要求时再专题学习。
- 以 2–3 次集中学习完成 RAG 应用入门，随后在 Agent 接入场景中实践。检索质量问题需要能定位到检索阶段，但不要求当前就掌握所有优化手段。

最终演示场景：用户上传一份有来源信息的公开研报或公告，提问“结合指定日期的行情与文档，比较两个板块的表现并说明依据”。系统按需要选择行情、资金、成分股、文档检索工具，输出事实、推断、来源、日期与数据缺口；对无法支持的因果结论保持明确限制。

MVP 包含：单 Agent、多工具调用、文档持久化检索、证据引用、至少一种真实行情来源、可查询的运行记录、可展示的界面、固定评估集、可复现启动方式。

后置内容：多 Agent、MCP 接入、复杂规划器、重排模型、混合检索、长期记忆。只有 MVP 跑通且评估表明需要时再选做。不做自动交易和收益预测承诺。

## 阶段路线

| 阶段 | 学习核心 | 项目交付物 | 用户负责 | 助手负责 | 阶段验收 |
| --- | --- | --- | --- | --- | --- |
| M0 基线与知识定位 | 读懂现有调用链；区分 Chat、工具调用与 Agent 循环 | 现状记录、可重复的单元测试入口 | 用一次请求解释循环和消息变化 | 文档、测试入口、辅助修补 | 用户能说明模型与系统各做什么；测试结果有记录 |
| M1 可靠的单 Agent | 停止条件、预算、技术重试与业务降级、上下文延续 | 完成/未完成/失败的运行结果，退出时保留 Trace | 设计并实现停止与降级策略 | 状态枚举、DTO、解析、异常适配、回归测试 | 正常结束、步数耗尽、工具失败、模型异常均有明确结果 |
| M2 知识库工具基础 | 应用层理解分块、Embedding、TopK、来源信息 | 上传一次、后续按问题检索的持久化知识库 | 能解释输入输出，判断结果是否相关，不要求手写存储与入库流程 | 入库/检索工程、文件管理、实体、存储适配和部署配置 | 工程：重启可检索、页码准确；学习：能解释一次检索并指出局限 |
| M3 Agent 使用文档证据 | RAG 与工具调用结合，证据不足处理，不可信文档边界 | 文档检索工具与带引用的研究回答 | 实现检索工具编排、证据组织与回答约束 | 跨模块客户端、DTO、来源展示和测试 | 可组合行情与文档；引用能定位原文；无证据不捏造；文档中的指令不改变系统任务 |
| M4 真实行情与数据质量 | 工具契约、时效性、失败降级与 Mock 的区别 | 至少一种真实数据适配器，可明确切换演示数据 | 设计工具选择与数据不足时的行为 | HTTP 适配、字段映射、缓存配置、限流基础代码 | 数据有来源和时间；超时可追踪；不会将 Mock 冒充真实行情 |
| M5 会话与可观测性 | 模型上下文与业务历史区别，成本与延迟 | 会话隔离、运行记录持久化、耗时/调用次数统计 | 设计 Agent 多轮上下文与历史裁剪 | 持久化实体、查询接口、日志、界面和工程配置 | 会话不串线；可回看失败过程；统计口径可解释 |
| M6 评估与作品交付 | 如何证明 Agent 有用，如何定位错误 | 评估集、基线报告、启动文档、演示视频/页面、面试讲稿 | 标注样例、分析失败、解释设计与取舍 | 评估脚本、部署文件、图示、文档排版 | 能复现演示并重跑评估；简历陈述均有代码或测量证据 |

建议安排：M0 半周以内；M1 2–3 周，重点实践状态、停止、工具失败与预算；M4 约 1 周；M5 1–2 周，重点实践多轮上下文；M2 的用户学习压缩为 2–3 次，M3 约 1 周用于 Agent 接入；M6 1–2 周用于评估与交付。总排期仍暂留 8–12 周，节省的 RAG 深挖时间用于 Agent 实践和失败复盘。助手补齐工程所需时间不计作用户已经学习的时间。
